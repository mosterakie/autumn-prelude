# 秋序后端 v1.0 功能点实施顺序表

> 依据：《秋序后端与 Agent 架构设计总结 v1.0》§13 实施顺序 + 《Repository / UoW / 并发一致性设计总结》§17 实施顺序，
> 并结合两份文档的依赖方向（§1.2）、模块边界（§2）、约束基线（§11 / §14）与会话验收标准（§14）合并为一条可执行的串行路线。
>
> 排序总原则：**先让数据库能证明不变量 → 再让数据访问层能原子改状态 → 再用真实 PostgreSQL 证明并发正确 → 再往上搭 Policy / Service / API / Agent / Worker → 最后用 CI 与横切验收锁死边界。**
> 核心纪律：并发验收（阶段 C）必须早于 API 与 Agent，不允许等到上层写完才补测试。

---

## 阶段 A：地基与数据库契约

目标：让"最终不变量"在数据库层先成立，后续所有代码都建立在已被约束保护的模型上。

- [ ] **A1. 工程骨架与依赖规则落地**
  - 建立包布局：`api/` `auth/` `policies/` `services/` `agent/` `repositories/` `jobs/` `workers/` `providers/` `storage/` `observability/` `db/` `tests/`
  - 配置 FastAPI + Pydantic、SQLAlchemy 2 异步会话、Alembic、PostgreSQL(+pgvector) 连接
  - 建立 `tests/unit` `tests/integration` `tests/concurrency` 三层目录
  - 产出：可 `pytest` 空跑、可 `alembic` 空迁移的骨架

- [ ] **A2. SQLAlchemy Model 基类与 Mixin**
  - `DeclarativeBase`
  - `Versioned`（乐观锁 version）、`Timestamped`（timestamptz）、`SoftDelete`（deleted_at/archived_at）

- [ ] **A3. 逐表声明模型与约束（第一批）**
  - `users` / `auth_sessions` / `auth_tokens` / `admin_factors` / `rate_limit_buckets` / `settings`
  - 关键点：`settings.content_acl_epoch`；邮箱规范化后唯一；敏感令牌只存哈希/密文
  - 产出：`alembic revision --autogenerate` 可识别全部变更

- [ ] **A4. Alembic 第一批迁移 + `alembic check`**
  - 执行迁移并跑 `alembic check`（模型与迁移必须无漂移）

- [ ] **A5. 第二批模型与约束：内容 / 发布 / 检索**
  - `resources`（**version 与 acl_version 分离**）、`resource_versions`、`publications`、`comments`、`knowledge_indexes`、`run_sources`
  - 约束：
    - `publications` Partial Unique Index `resource_id WHERE revoked_at IS NULL`
    - `comments` `UNIQUE(author_id, client_id)`

- [ ] **A6. 第三批模型与约束：Run / 配额 / Job / 调用记录 / 审计**
  - `conversations`、`runs`、`run_events`、`quota_buckets`、`quota_reservations`、`jobs`、`provider_calls`、`audit_events`、`actions`
  - 约束清单（缺一不可）：
    - `runs` `UNIQUE(user_id, idempotency_key)`
    - `runs` Partial Unique Index：同 conversation 的非终态 run 唯一
    - `quota_buckets` `UNIQUE(user_id, window_start)`、`CHECK(used>=0)`、`CHECK(reserved>=0)`
    - `quota_reservations` `UNIQUE(run_id)`、`CHECK(amount=1)`
    - `provider_calls` 合法状态 `CHECK` + `UNIQUE(job_id, purpose, attempt_no)`
    - `jobs` 状态 / lease 字段 `CHECK`
    - `run_events` `PRIMARY KEY / UNIQUE(run_id, seq)`
  - 产出：Alembic 第二批迁移 + `alembic check` 通过

**阶段 A 完成判据**：所有 UNIQUE / CHECK / FK / Partial Unique Index 在真实 PostgreSQL 上创建成功，`alembic check` 无漂移。

## 阶段 B：UoW 与 Repository 原子状态转换

目标：Repository 成为"原子状态转换 API"，而不是 CRUD 包装层。**此阶段不写任何业务 Service。**

- [ ] **B1. 最小 UoW 实现**
  - 一个 UoW = 一个数据库事务，进入时构造全部 Repository 并共享同一 `AsyncSession`
  - 退出统一 commit / rollback；Repository 内**禁止 commit**，只允许 flush
  - 明确：`AsyncSession` 不跨并发协程共享

- [ ] **B2. Repository 基类与能力类型**
  - `RepositoryBase`（仅持有 session，不假设主键）
  - `UUIDRepository`（`get` / `get_or_raise` / `get_for_update` / `get_for_update_or_raise`；`Setting` 等 str 主键表自实现，不硬套）
  - `VersionedMixin`（单语句 CAS：`WHERE id=? AND version=? RETURNING`，0 行 → `OptimisticLockError`）
  - `AppendOnlyRepository`（**不提供通用 `record(**fields)`**）
  - `ControlledMutable` 约定（只用领域转换方法，不暴露通用 update/delete）

- [ ] **B3. 统一错误映射层**
  - DB 约束错误 → 领域错误：`ConflictError` / `OptimisticLockError` / `DomainError`
  - 状态转换统一形状：`UPDATE ... WHERE id=? AND state=:expected RETURNING`，0 行 → `ConflictError`

- [ ] **B4. Run Repository（幂等 + 事件序号）**
  - `create_idempotent`：`INSERT ... ON CONFLICT DO NOTHING RETURNING` → 冲突回读 → 比对 `request_hash` → 相同返回原 run / 不同 `ConflictError`
  - `RunEventRepository.emit()`：通过 `UPDATE runs SET next_event_seq = next_event_seq + 1 RETURNING next_event_seq - 1` **原子分配 seq**，禁止外部指定 seq

- [ ] **B5. Quota Repository（首次创建 + 预留状态机）**
  - Bucket 首次创建：`INSERT ... ON CONFLICT (user_id, window_start) DO NOTHING` **再** `SELECT ... FOR UPDATE`（不能指望锁住不存在的行）
  - Reservation 幂等：`INSERT ... ON CONFLICT (run_id) DO NOTHING RETURNING`；仅首次插入才 `bucket.reserved += amount`；冲突分支 `SELECT existing FOR UPDATE` 校验 `bucket_id` / `amount`
  - 状态机方法：`reserve` / `charge` / `release` / `refund`，全部**不倒退**（charged 不退回 reserved，refunded 不二次改 used）
  - 超额 → 抛异常让整个 UoW 回滚（连带撤销刚插入的 reservation）

- [ ] **B6. Job Repository（SKIP LOCKED + lease）**
  - `claim`：`WHERE status='queued' AND available_at<=now() ORDER BY available_at, id FOR UPDATE SKIP LOCKED LIMIT 1` → `status='running'` / `lease_token` / `lease_expires_at` / `attempts+=1`
  - `heartbeat` / `finish`：**必须匹配 `lease_token` 且 `status='running'`**，0 行表示 lease 已丢失
  - `reclaim`（过期 lease 回收）留到阶段 F

- [ ] **B7. ProviderCall Repository（受限状态机）**
  - `prepared → dispatched → succeeded | failed | unknown`
  - `settle_*` 必须 `WHERE status='dispatched'`，0 行 → `ConflictError`
  - `mark_dispatched`；`unknown` 不得当作"失败且零成本"

- [ ] **B8. Comment Repository（幂等 + 跨行不变量）**
  - `(author_id, client_id)` 去重 + `request_hash` 语义判等
  - `request_hash` 计算：稳定 JSON 序列化 SHA-256；正文仅 CRLF/CR → LF，**不 strip、不折叠空白、不做 NFKC**；`resource_id` / `parent_id` / `body` 全部入 hash
  - `create_or_get`：fast-path SELECT → 父评论同事务校验（父存在、父无 parent、resource_id 一致、父未删除）→ `INSERT ... ON CONFLICT DO NOTHING RETURNING` → 竞争输家回读比对
  - **明确记录：父评论跨行不变量由 Repository 事务内校验承担，DB 只能靠 trigger**

- [ ] **B9. Publication Repository（发布锁语义）**
  - 方法名 `publish_under_resource_lock`，显式体现前置条件
  - 锁 Resource 行 → 串行化 `publication_no` 的 `MAX()+1`
  - 撤销旧 publication → 插入新 publication → `acl_version++`（**不递增 resources.version**）→ `content_acl_epoch++`
  - `revoke` 只动可见性：立即阻断公开读取，索引/缓存清理交给异步 job

- [ ] **B10. Resource / Conversation / Memory 的 Versioned 方法**
  - 编辑原稿、标题、标签、私密备注、归档 → 递增 `resources.version`
  - publish / revoke / 软删除 / 恢复 → 递增 `acl_version`

- [ ] **B11. Cursor Pagination 统一实现**
  - 统一 `(created_at DESC, id DESC)` 复合游标，**排序键与游标键必须一致**
  - `LIMIT :limit + 1` 探测下一页
  - `Cursor.decode` 捕获非法 base64 / UUID / datetime / **naive datetime** → 统一 HTTP 400
  - 未来按 `updated_at` 排序需定义独立 Cursor 类型

- [ ] **B12. AuditEvent（AppendOnly）**
  - 只暴露 `record()`；`before_version` / `after_version` 专指 `resources.version`，ACL 前后值写入 `metadata`

**阶段 B 完成判据**：所有幂等/状态转换方法都通过 UPSERT + UNIQUE 仲裁，代码中不存在"先 SELECT 后 INSERT"承担并发正确性的写法。

## 阶段 C：真实 PostgreSQL 并发验收（关键闸门，必须在此完成）

目标：不等 API、不等 Agent，先把 5 个并发用例跑绿。

- [ ] **C1. 测试基础设施**
  - 真实 PostgreSQL + pgvector 实例（测试用容器/独立库）
  - 并发驱动工具（多协程 + 独立连接、barrier 同步起跑）
  - **明确禁止**：SQLite 或 Mock Repository 替代（无法证明 ON CONFLICT / FOR UPDATE / SKIP LOCKED / Partial Unique Index / 隔离级别）

- [ ] **C2. Case 1 — 同 `idempotency_key` 并发 Run**
  - 期望：一个创建、一个返回原 run；`request_hash` 不同 → 冲突

- [ ] **C3. Case 2 — 两个不同 run 并发首次创建当天 bucket**
  - 期望：`quota_buckets=1`，`reservations=2`，`bucket.reserved=2`

- [ ] **C4. Case 3 — 两个 worker 抢同一 job**
  - 期望：仅一个 claim 成功；旧 lease 的 `finish` 被拒绝

- [ ] **C5. Case 4 — 同一 `run_id` 并发 reserve 两次**
  - 期望：`reservation=1`，`bucket.reserved=1`，两边得到等价成功结果

- [ ] **C6. Case 5 — 同一 `run_id` 并发 reserve 但 amount 不同**
  - 期望：一方成功，另一方 `ConflictError`

- [ ] **C7. 约束级单测**：Partial Unique Index（同 conversation 非终态 run、publications 现行版本）与各 CHECK 的负向用例

**阶段 C 完成判据**：5 个用例全部在 CI 可重复跑绿。**未通过前不进入阶段 D。**

## 阶段 D：纯 Policies

- [ ] **D1. `ActorContext`（frozen dataclass）**
  - 字段：`user_id` / `role` / `auth_session_id` / `step_up_expires_at` / `capabilities` / `scope_epoch`
  - 三个构造入口的约定（此时只定接口，实现随所属层落地）：
    - API：从 Cookie 会话重建
    - Agent：从 run 绑定的 `auth_session_id` 重建，**不信任 checkpoint 里的旧权限**
    - Worker：从 job 元数据与服务端记录重建，不带浏览器 Cookie 明文
  - **不变量：模型/工具参数不能构造 ActorContext；工具只接业务参数**

- [ ] **D2. `PolicyFacts` 不可变结构**

- [ ] **D3. 纯判定函数**
  - 形态固定：`policy.evaluate(actor, facts) -> Decision`
  - **判定函数零 I/O**；简单场景由 service 直接组装 facts

- [ ] **D4. Capability 与角色矩阵**（anonymous / member / owner）
  - 含 step-up 过期判定、私密对象与不存在对象统一 404、需升级时 403 `STEP_UP_REQUIRED`

- [ ] **D5. `policies/loader.py`（可选只读装配层）**
  - 只服务复杂多表只读 facts 装配，**不得演变成第二个 service / repository 层**

- [ ] **D6. `content_acl_epoch` 变化语义**
  - 定义 `run.invalidated` 触发条件与旧 generation 的处理契约（`ACL_CONTEXT_INVALIDATED`）

**阶段 D 完成判据**：policy 层为纯函数，可脱离 DB 单测；无任何 I/O 与 ORM 调用。

## 阶段 E：Services（按此顺序，每个配集成测试）

顺序依据文档 §13：`publish → accept_run → comments → quota`。

- [ ] **E1. Publication Service**
  - 发布事务五步：锁 Resource 校验 `expected_version` + `revision_id` → 按类型白名单构造公开投影 → 撤销旧 publication/插入新 publication → `acl_version++` 且 `content_acl_epoch++` → 同事务写 action / audit / knowledge-index job
  - commit 后返回 `public_url` 与实际公开字段
  - 公开读取必须联表过滤未删除/未归档资源
  - **公开索引只由公开投影构建，禁止复用私人 chunk 加 public 标记**

- [ ] **E2. Run 受理 Service（`accept_run`）**
  - 事务内顺序：lock user → lock conversation → 校验身份/mode/cooldown/step-up → `runs.create_idempotent` → `quota_bucket INSERT ON CONFLICT DO NOTHING → SELECT FOR UPDATE` → `quota_reservation.reserve` → 插入 user message → `enqueue run.dispatch` → commit
  - 幂等语义：同 key 同 hash 返回原 run；同 key 不同 hash → 409 `IDEMPOTENCY_CONFLICT`
  - **已有幂等请求不重复占用 AI 速率窗口**
  - 时间语义：日额度按 Asia/Shanghai 00:00 切分，DB 统一 UTC；run 固定归属受理时 bucket，跨午夜恢复不换桶、不重扣；配置降低只约束后续受理

- [ ] **E3. Comment Service**
  - 调用 B8 的 `create_or_get`；错误语义与 404/409 映射边界

- [ ] **E4. Quota Service**
  - 预留/结算对外流程：供应商调用前失败可 `release`；调用后停止不重复 `refund`/扣次
  - 后台：过期 Reservation 清理（先定接口，实现随阶段 F）

- [ ] **E5. Storage Service（staging / finalize / delete 流程编排）**
  - Upload：`staging/{uuid}` → hash/MIME/size 校验 → UoW 写 `status=staged` + enqueue `storage.finalize` → worker 转永久 → UoW `status=ready`
  - Delete：UoW 软删除 + 立即阻断访问 + enqueue `storage.delete` → worker 物理删除 → 失败保持 `pending_delete` 待重试
  - **物理 I/O 不参与数据库事务**

- [ ] **E6. Knowledge / RAG Service**
  - 网页与文件统一落为 `resource_versions`
  - 私人版本与公开 publication 分别建 `knowledge_indexes`
  - 检索：先选允许访问的 active index → 向量相似度 → 可选 rerank
  - `run_sources` 记录实际进入模型的全部来源，绑定 revision/publication/acl_version/片段位置

- [ ] **E7. Action Service（确认/补充的持久等待）**
  - action 幂等身份与语义判等：目标、版本、参数摘要 hash

- [ ] **E8. Service 层横切验证**
  - 逐 service 断言：**所有外部 I/O 都在 UoW 之外**（I/O 前结束当前 UoW，I/O 后需要落库则开新 UoW）
  - 一个 service operation 允许包含多个短 UoW

**阶段 E 完成判据**：每个 service 有对应集成测试；无任何 UoW 跨越 LLM / 搜索 / 对象存储 / 邮件。

## 阶段 F：API 层

顺序依据文档 §13：先 auth/resources，再 runs + SSE。

- [ ] **F1. API 骨架**
  - `deps`（ActorContext 从 Cookie 会话重建）、`errors`（DomainError → HTTP 映射）、统一响应/校验
  - **硬约束：api 不直接访问 ORM、不直接调 provider；仅依赖 services / auth / observability**

- [ ] **F2. auth 模块**
  - 密码：Argon2id；邮箱规范化后唯一
  - 会话：高熵随机令牌，DB 只存令牌哈希；生产 Cookie `Secure` / `HttpOnly` / `SameSite=Lax` / `Path=/` / `__Host-` 前缀；开发环境独立 Cookie 名
  - CSRF：服务端密钥绑定 `session_id` + `csrf_version` 签名；所有已认证写请求同时验 CSRF 与可信 Origin
  - TOTP、一次性令牌、密码重置；登录 / step-up / 重置成功后**轮换会话并递增 `csrf_version`**
  - 站长 bootstrap：本地引导 + 强制 TOTP；站长账号不可公开注册；**站长身份不自动获得他人聊天读取权**

- [ ] **F3. auth 路由 + 会话与 step-up 中间件**

- [ ] **F4. resources 路由**
  - 资源 CRUD（走 E 层 service）、私人备注绝不进入公开 API
  - 统一游标分页接入

- [ ] **F5. publications / public 读取路由**
  - 公开读取联表当前 publication + 未删除/未归档资源
  - 撤回后立即阻断；私密对象与不存在对象对外一致 404

- [ ] **F6. runs 路由 + Run 受理接口**
  - 接收 idempotency key，走 `accept_run`；冲突映射 409 `IDEMPOTENCY_CONFLICT`

- [ ] **F7. SSE（流式输出）**
  - `messages` 存完整消息文本；`run_events` 只存事件、对象 ID、版本与必要元数据
  - SSE 使用**累计消息快照**，前端按 `content_version` 替换
  - 每个读取批次重新校验会话、step-up 与来源权限
  - 权限撤回后停止后续输出（已发送字节不可收回）；**连接中断不等于取消 run**

- [ ] **F8. comments / quota / actions 路由**

**阶段 F 完成判据**：两个用户不能互读 conversation / run / event / source / file / action；CSRF + Origin 校验对全部已认证写请求生效。

## 阶段 G：Agent Runtime（最小可用）

- [ ] **G1. LangGraph 骨架 + 最小节点集**
  - 工作流骨架：鉴权/归属 → 冷却/额度/并发检查 → 载入权限与上下文 → 理解目标并选择获准工具 → [需确认/补充] 持久等待 → 恢复时重新鉴权并重建上下文 → 执行 → 记录来源与结果 → 完成或继续（受预算限制）

- [ ] **G2. 上下文与预算**
  - 一个 conversation 固定 `public` 或 `owner` 模式；一个 ask 创建一个 run
  - `thread_id` **仅由服务端生成**，与 conversation + mode 绑定
  - checkpoint 只是恢复依据，**不是权限来源**

- [ ] **G3. 两个薄适配器工具**
  - 工具仅接业务参数，**ActorContext 由服务端注入**；工具不直接绕过 service
  - 验证点：工具是 service 的薄适配器

- [ ] **G4. 安全边界落地**
  - 网页 / PDF / Word / 检索内容都是资料，**不构成用户授权**
  - 发布、删除、设置修改必须追溯到用户明确请求或已确认 action

- [ ] **G5. ACL 变化时的旧 generation 处理**
  - `content_acl_epoch` changed → emit `run.invalidated` → 尽量 cancel provider stream → 不再从旧 context 继续生成 → run `failed/cancelled` + `error_code=ACL_CONTEXT_INVALIDATED` → 需继续则重建上下文后开启新的合法执行阶段
  - 主状态保持有限集合，具体原因用 `error_code` / `terminal_reason`，**不为每种终止原因扩张 `runs.status`**

- [ ] **G6. 恢复路径**
  - 从 run 绑定的 `auth_session_id` 重建 ActorContext；恢复时重新鉴权

- [ ] **G7. `run_sources` 落库**
  - 来源与结果记录，绑定 revision/publication/acl_version/片段位置

**阶段 G 完成判据**：agent 测试通过；工具无法伪造用户身份、权限、会话或 step-up 状态。

## 阶段 H：Workers 与 Job 基础设施

- [ ] **H1. `jobs.queue` 基础设施**
  - enqueue / claim / heartbeat / finish / reclaim
  - **不包含业务 handler**，不认识 services 或 handler（消除循环依赖）

- [ ] **H2. Worker 主循环 + registry + entrypoint**
  - 执行形状：[UoW 1] claim job → lease_token → commit → [事务外] handler / agent.runtime / provider / HTTP / parsing + heartbeat → [UoW 2] finish(job_id, lease_token, result)

- [ ] **H3. `run.dispatch` handler → `agent.runtime`**
  - 落定 workers → agent.runtime 的允许依赖

- [ ] **H4. `storage.finalize` / `storage.delete` handlers**

- [ ] **H5. `knowledge.index` handler**
  - 索引与缓存清理异步收敛；公开索引只从公开投影构建

- [ ] **H6. lease 丢失语义**
  - `heartbeat` 0 行 → 停止新的副作用；若可取消上游则尝试 cancel
  - 即使旧外部请求最终返回，也**不得再 finish 或写正式结果**
  - 明确：lease 只控制"提交结果资格"，不保证已发出的外部请求被撤销

- [ ] **H7. At-least-once 与 ProviderCall 集成**
  - provider 支持 idempotency key 时透传 `provider_call_id`（或 `job_id + purpose + attempt_no`）
  - provider 不支持幂等 → 接受 at-least-once；`unknown` **不自动重放**

- [ ] **H8. 后台收敛任务（第六步）**
  - lease reclaim（过期 job 回收）
  - Provider reconciliation（unknown 对账）
  - 过期 Reservation 清理
  - pending_delete 重试
